Every call you make to a verification endpoint draws from a prepaid credit balance tied to your IDTO account. Understanding exactly when credits are consumed — and when they are not — helps you budget accurately and avoid unexpected service interruptions. v2 also enforces user consent at the API level, making your compliance posture explicit in every request.

## How Credits Work

<CardGroup cols={2}>
  <Card title="Credits consumed" icon="circle-check">
    A credit is deducted when IDTO successfully queries the upstream registry, regardless of whether a matching record is found. Successful verifications and **IDTO_202 (no record found)** both consume a credit.
  </Card>
  <Card title="Credits not consumed" icon="circle-xmark">
    No credit is deducted for input validation failures, authentication rejections, missing user consent, rate-limit responses, or service errors. You only pay for complete lookups.
  </Card>
</CardGroup>

### The `billed` Field

Every v2 response contains a `billed` boolean that tells you definitively whether your account was charged for that specific call:

```json
{
  "status": "success",
  "billed": true,
  ...
}
```

Use `billed` in your logging pipeline to reconcile API usage against your account balance. If `billed` is `false`, you can safely retry the request after fixing the underlying issue — you will not be double-charged for the failed attempt.

### When `billed` is `true`

| Scenario | `status` | `error_code` | `billed` |
|---|---|---|---|
| Successful verification, record found | `success` | `null` | `true` |
| Successful query, **no record found** (IDTO_202) | `error` | `IDTO_202` | `true` |

### When `billed` is `false`

| Scenario | `error_code` | `billed` |
|---|---|---|
| Missing or invalid request field | `IDTO_001` | `false` |
| User consent missing | `IDTO_005` | `false` |
| Rate limit exceeded | `IDTO_006` | `false` |
| Insufficient credits | `IDTO_009` | `false` |
| Service error | `IDTO_007` / `IDTO_008` | `false` |
| Auth failure (wrong credentials) | — (401) | `false` |

## IDTO_202: No Record Found Is Still Billed

<Warning>
When IDTO queries a government registry and the record genuinely does not exist, the response carries `error_code: "IDTO_202"` with `billed: true`. A full lookup was executed — the registry confirmed there is no match. This is intentional and mirrors the cost model of the underlying data sources.

Do not treat `IDTO_202` as a free failure. Budget for a portion of your verifications returning no record, particularly for less-populated registries.
</Warning>

## Checking Your Balance

Retrieve your current credit balance with a `GET` request to `/me/balance`. This endpoint uses Bearer JWT authentication from your login token rather than the `X-Client-ID` / `X-API-KEY` header pair.

<Steps>
  <Step title="Log in to get an access token">
    ```bash
    curl --request POST \
      --url https://prod.idto.ai/auth/login \
      --header 'Content-Type: application/json' \
      --data '{
        "client_id": "<your_client_id>",
        "api_key": "<your_api_key>"
      }'
    ```
    The response contains an `access_token`. Copy it for the next step.
  </Step>
  <Step title="Call GET /me/balance">
    ```bash
    curl --request GET \
      --url https://prod.idto.ai/me/balance \
      --header 'Authorization: Bearer <access_token>'
    ```
  </Step>
</Steps>

### Checking Balance in Python

```python
import requests

# Step 1: Authenticate
login_resp = requests.post(
    "https://prod.idto.ai/auth/login",
    json={
        "client_id": "<your_client_id>",
        "api_key": "<your_api_key>",
    },
)
login_resp.raise_for_status()
access_token = login_resp.json()["access_token"]

# Step 2: Fetch balance
balance_resp = requests.get(
    "https://prod.idto.ai/me/balance",
    headers={"Authorization": f"Bearer {access_token}"},
)
balance_resp.raise_for_status()

balance = balance_resp.json()
print(f"Current balance: {balance['data']['credits']} credits")

# Step 3: Alert if low
MINIMUM_CREDITS = 100
if balance["data"]["credits"] < MINIMUM_CREDITS:
    print("WARNING: Credit balance is low. Recharge at https://idto.ai")
```

<Tip>
Integrate a balance check into your application's health-check or monitoring routine. Trigger an alert when credits fall below your expected daily consumption so you can recharge before hitting `IDTO_009`.
</Tip>

## User Consent in v2

All v2 verification endpoints require you to pass `"user_consent": true` in the request body. This field represents your application having obtained the end user's informed consent to verify their identity using their government-issued documents or personal details.

```json
{
  "pan": "ABCDE1234F",
  "name": "Ravi Kumar",
  "user_consent": true
}
```

If you omit `user_consent` or set it to `false`, the API immediately rejects the request with:

```json
{
  "status": "error",
  "message": "User consent is required to proceed with verification.",
  "error_code": "IDTO_005",
  "data": null,
  "billed": false,
  "tranx_id": "f6a7b8c9-d0e1-2345-fabc-456789012345",
  "timestamp": "2026-07-11T10:25:00.000000"
}
```

<Note>
`IDTO_005` rejections are never billed. You can correct the request and resend without losing a credit.
</Note>

### Consent Best Practices

<Accordion title="What does 'user consent' mean in practice?">
  Before calling any verification endpoint, your application must present the end user with a clear statement explaining that their identity document details will be submitted to a third-party verification service. The user must explicitly agree — for example, by ticking a checkbox or tapping an "I Agree" button — before you fire the API call. Store a record of this consent (timestamp, user ID, consent text version) in your own database for audit purposes.
</Accordion>

<Accordion title="Do I need fresh consent for every API call?">
  Consent is bound to a specific verification action. If your flow triggers multiple verification calls for the same user in one session (for example, PAN + Aadhaar), you may cover both with a single consent screen as long as the scope is clearly disclosed. Do not silently reuse consent from a previous session without informing the user.
</Accordion>

<Accordion title="Does v1 enforce user consent?">
  No. v1 endpoints accept requests without `user_consent`. However, you should still obtain and record user consent in your application for regulatory compliance, even when using v1.
</Accordion>

## Avoiding IDTO_009 (Insufficient Credits)

<Tip>
Recharge your account at [idto.ai](https://idto.ai) before your balance reaches zero. An `IDTO_009` response halts all verification calls until credits are added, which can disrupt real-time user-facing flows.
</Tip>

Implement a proactive recharge strategy:

1. **Set a low-balance alert** — poll `/me/balance` periodically and alert your team when credits drop below a threshold.
2. **Monitor `billed: true` events** — count billable calls in your logs to forecast burn rate.
3. **Gracefully handle IDTO_009** — show users a friendly error rather than an unhandled exception, and queue the verification for retry after a recharge.
