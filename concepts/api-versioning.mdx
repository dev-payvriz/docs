IDTO runs two API versions concurrently. Version 1 (v1) was the original release and remains available for endpoints that have not yet been migrated. Version 2 (v2) is the current standard and introduces a consistent response envelope, structured error codes, mandatory user consent, and idempotency support. For all new integrations, use v2 wherever it is available.

## Path Prefixes

Every endpoint belongs to exactly one version based on its URL prefix:

- **v1** endpoints live under `/verify/*` — for example, `/verify/pan`
- **v2** endpoints live under `/v2/verify/*` — for example, `/v2/verify/pan`

Both versions share the same production base URL: `https://prod.idto.ai`

## What Changed in v2

The table below summarises the most important differences between the two versions.

| Feature | v1 | v2 |
|---|---|---|
| **Response envelope** | `{ ..., chargeble, user_consent }` (flat, inconsistent) | `{ status, message, error_code, data, billed, tranx_id, timestamp }` |
| **Error shape** | `{ "detail": { "status": "...", "message": "..." } }` | Same flat envelope as success responses |
| **User consent** | Optional — not enforced | Required — `user_consent: true` must be present in every request body |
| **Idempotency** | Not supported | Supported via optional `Idempotency-Key` request header |
| **Error codes** | None / ad-hoc strings | Standardised `IDTO_*` codes in `error_code` field |
| **Transaction ID** | Not present | Every response includes a `tranx_id` UUID for support correlation |

## Which Version Should You Use?

<Note>
Use v2 for all new integrations. It provides predictable error handling, structured billing signals, and safe retry semantics through idempotency keys.
</Note>

A small number of endpoints do not yet have a v2 equivalent. For those, continue using v1:

- `business_pan` — `/verify/business_pan`
- `pan_nsdl` — `/verify/pan_nsdl`
- `passport` — `/verify/passport`
- `voter_id` — `/verify/voter_id`

Check the individual endpoint reference pages for the canonical version label and path.

## Side-by-Side Comparison: PAN Verification

The following example shows the same PAN verification request made in both versions so you can see exactly what differs in the request body and the response structure.

<CodeGroup>

```bash v1 – POST /verify/pan
curl --request POST \
  --url https://prod.idto.ai/verify/pan \
  --header 'Content-Type: application/json' \
  --header 'X-Client-ID: <your_client_id>' \
  --header 'X-API-KEY: <your_api_key>' \
  --data '{
    "pan": "ABCDE1234F",
    "name": "Ravi Kumar"
  }'
```

```bash v2 – POST /v2/verify/pan
curl --request POST \
  --url https://prod.idto.ai/v2/verify/pan \
  --header 'Content-Type: application/json' \
  --header 'X-Client-ID: <your_client_id>' \
  --header 'X-API-KEY: <your_api_key>' \
  --data '{
    "pan": "ABCDE1234F",
    "name": "Ravi Kumar",
    "user_consent": true
  }'
```

</CodeGroup>

<CodeGroup>

```json v1 – Success Response
{
  "pan": "ABCDE1234F",
  "name": "Ravi Kumar",
  "status": "VALID",
  "chargeble": true,
  "user_consent": null
}
```

```json v2 – Success Response
{
  "status": "success",
  "message": "PAN verified successfully.",
  "error_code": null,
  "data": {
    "pan": "ABCDE1234F",
    "name": "Ravi Kumar",
    "status": "VALID"
  },
  "billed": true,
  "tranx_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "timestamp": "2026-07-11T10:20:30.123456"
}
```

</CodeGroup>

<CodeGroup>

```json v1 – Error Response
{
  "detail": {
    "status": "error",
    "message": "Invalid PAN format."
  }
}
```

```json v2 – Error Response
{
  "status": "error",
  "message": "Invalid or missing field: pan.",
  "error_code": "IDTO_001",
  "data": null,
  "billed": false,
  "tranx_id": "b2c3d4e5-f6a7-8901-bcde-f12345678901",
  "timestamp": "2026-07-11T10:20:31.456789"
}
```

</CodeGroup>

## Migration Checklist

When upgrading an existing v1 integration to v2, work through this checklist:

<Steps>
  <Step title="Update the endpoint path">
    Change `/verify/<endpoint>` to `/v2/verify/<endpoint>` in every API call.
  </Step>
  <Step title="Add user_consent to every request body">
    Append `"user_consent": true` to all request payloads. Without it, every call returns `IDTO_005`.
  </Step>
  <Step title="Update your response parser">
    Read `status`, `error_code`, and `data` from the new envelope instead of the v1 flat structure. Replace checks on `chargeble` with checks on `billed`.
  </Step>
  <Step title="Adopt IDTO_* error handling">
    Map each `IDTO_*` error code to your application's retry or alert logic. See the [error codes reference](/error-codes) for the full list.
  </Step>
  <Step title="Optionally add Idempotency-Key">
    Generate a UUID v4 per request and pass it as the `Idempotency-Key` header to enable safe retries without duplicate billing.
  </Step>
</Steps>
