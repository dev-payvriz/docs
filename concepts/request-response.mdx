Every request you send to the IDTO API follows a consistent pattern: a JSON or multipart body posted to a versioned path under the production base URL, authenticated with your client credentials, and answered with a predictable envelope. Understanding this envelope — especially how billing signals and error codes appear together — is the foundation for building a reliable integration.

## Base URL

All endpoints are hosted at a single production origin:

```
https://prod.idto.ai
```

There is no separate staging origin. Use your sandbox credentials during development and switch to production credentials when you go live.

## Content Types

<Tabs>
  <Tab title="JSON (most endpoints)">
    Send `Content-Type: application/json` for all identity, document number, and business verification endpoints. The request body must be a valid JSON object.

    ```bash
    --header 'Content-Type: application/json' \
    --data '{ "pan": "ABCDE1234F", "user_consent": true }'
    ```
  </Tab>
  <Tab title="Multipart (image & file uploads)">
    Send `Content-Type: multipart/form-data` whenever the endpoint accepts a file or image. Affected endpoint categories include:

    - **OCR** — Aadhaar card, PAN card, driving licence, passport image extraction
    - **Face Match** — comparing two face images
    - **Liveness** — selfie/video liveness check
    - **Aadhaar QR** — parsing a QR code from an Aadhaar image file

    ```bash
    --header 'Content-Type: multipart/form-data' \
    --form 'image=@/path/to/aadhaar_front.jpg' \
    --form 'user_consent=true'
    ```
  </Tab>
</Tabs>

## Authentication Headers

<Note>
Every verification endpoint (`/verify/*` and `/v2/verify/*`) requires both headers below. Account-management endpoints (`/me/balance`, `/auth/login`) use `Authorization: Bearer <access_token>` instead.
</Note>

```http
X-Client-ID: <your_client_id>
X-API-KEY:   <your_api_key>
```

## The v2 Response Envelope

Every v2 response — whether a success, a validation error, or a downstream service failure — returns the same top-level JSON object. This consistency means you can always parse the same structure regardless of HTTP status code.

<ResponseField name="status" type="string" required>
  Either `"success"` or `"error"`. Use this field for your primary branch — it is never absent.
</ResponseField>

<ResponseField name="message" type="string" required>
  A human-readable description of the outcome. Suitable for logging; do not display raw to end users in production.
</ResponseField>

<ResponseField name="error_code" type="string | null" required>
  `null` on a fully successful response. On any failure, contains a standardised `IDTO_*` code you can map to application logic. See the error codes table below.
</ResponseField>

<ResponseField name="data" type="object | null" required>
  The verification result payload. Its schema varies by endpoint. `null` when `status` is `"error"`.
</ResponseField>

<ResponseField name="billed" type="boolean" required>
  `true` when a credit was consumed for this request; `false` when no charge was applied (for example, on input validation failures, authentication rejections, or rate-limit responses).
</ResponseField>

<ResponseField name="tranx_id" type="string (UUID)" required>
  A unique identifier for this API call. Include this value in any support request so the IDTO team can locate the exact transaction in their logs.
</ResponseField>

<ResponseField name="timestamp" type="string (ISO 8601)" required>
  The server-side timestamp at which the response was generated, in UTC. Format: `YYYY-MM-DDTHH:MM:SS.ffffff`.
</ResponseField>

## Standard Error Codes

| Code | HTTP Status | Meaning |
|---|---|---|
| `IDTO_001` | 400 / 422 | Invalid or missing field in the request body |
| `IDTO_004` | 409 | Duplicate idempotency key — a request with this key is already in flight |
| `IDTO_005` | 400 | User consent not provided (`user_consent: true` missing) |
| `IDTO_006` | 429 | Rate limit exceeded — slow down and retry |
| `IDTO_007` | 500 | Service configuration error — contact support |
| `IDTO_008` | 503 | Service temporarily unavailable — retry with back-off |
| `IDTO_009` | 402 | Insufficient credits — recharge your account |
| `IDTO_202` | 200 | No matching record found — verification ran, credit consumed |
| `IDTO_203` | 202 | Verification in progress — use the async polling endpoint |
| `IDTO_204` | 422 | No readable QR code found in the uploaded image |
| `IDTO_205` | 422 | Wrong OTP or expired OTP session |
| `IDTO_206` | 429 | Maximum OTP attempts exceeded for this session |
| `IDTO_207` | 404 | Async result not yet available or key not found |

## IDTO_202: Billed Even With No Record

<Warning>
`IDTO_202` is a special case: the HTTP status is `200` and `billed` is `true`, but `data` is `null` and `error_code` is `"IDTO_202"`. This means the request was valid and a complete lookup was performed against the upstream registry — no record existed, but the check itself consumed a credit.

Always inspect `error_code` in addition to `status` to distinguish a genuine match from a no-record result.
</Warning>

## Handling Responses in Code

<Tabs>
  <Tab title="Python">
    ```python
    import requests

    response = requests.post(
        "https://prod.idto.ai/v2/verify/pan",
        headers={
            "X-Client-ID": "<your_client_id>",
            "X-API-KEY": "<your_api_key>",
            "Content-Type": "application/json",
        },
        json={
            "pan": "ABCDE1234F",
            "name": "Ravi Kumar",
            "user_consent": True,
        },
    )

    body = response.json()

    if body["status"] == "success":
        print("Verified:", body["data"])
    elif body["error_code"] == "IDTO_202":
        # Billed but no record — treat as an unmatched identity
        print("No record found. Transaction:", body["tranx_id"])
    else:
        print(f"Error {body['error_code']}: {body['message']}")
    ```
  </Tab>
  <Tab title="Node.js">
    ```javascript
    const response = await fetch("https://prod.idto.ai/v2/verify/pan", {
      method: "POST",
      headers: {
        "X-Client-ID": "<your_client_id>",
        "X-API-KEY": "<your_api_key>",
        "Content-Type": "application/json",
      },
      body: JSON.stringify({
        pan: "ABCDE1234F",
        name: "Ravi Kumar",
        user_consent: true,
      }),
    });

    const body = await response.json();

    if (body.status === "success") {
      console.log("Verified:", body.data);
    } else if (body.error_code === "IDTO_202") {
      console.log("No record found. Transaction:", body.tranx_id);
    } else {
      console.error(`Error ${body.error_code}: ${body.message}`);
    }
    ```
