Most IDTO endpoints respond inline, you send a request, you get a result. A few can't: the underlying check takes longer than a single HTTP request should reasonably block for, or it's inherently multi-step (upload a document, wait for it to process, fetch the result). Both cases use the same building block: a pending state you poll until it resolves.

## The pending envelope: `IDTO_203`

`IDTO_203` is the shared taxonomy code for "this isn't done yet" (`kernel/errors.py`): HTTP 202, message "Verification is still in progress. Retrieve the result using reference_id.", and it is never billed. Any endpoint across the API can in principle hand back a `202` with this code instead of a final result.

The concrete, implemented version of this today lives on a specific set of v1 endpoints: `POST /verify/employment_history`, `POST /verify/uan_passbook/without_otp`, and `POST /verify/pf_employee_passbook`. Each of these tries to complete synchronously for up to 20 seconds. If the underlying job hasn't finished by then, you get:

```http
HTTP/1.1 202 Accepted
Retry-After: 5
Content-Type: application/json
```

```json
{
  "status": "pending",
  "message": "Verification is still in progress. Retrieve the result using reference_id.",
  "error_code": "IDTO_203",
  "reference_id": "b6e1f2a0-1234-4abc-9def-0123456789ab",
  "retry_after_seconds": 5,
  "data": null
}
```

Poll for the result with:

```bash
curl --request GET \
  --url https://prod.idto.ai/verify/result/b6e1f2a0-1234-4abc-9def-0123456789ab \
  --header "X-Client-ID: $IDTO_CLIENT_ID" \
  --header "X-API-Key: $IDTO_API_KEY"
```

While the job is still running, you get the same `202` / `IDTO_203` envelope back, with the same `reference_id`. Once it finishes, `GET /verify/result/{reference_id}` returns the completed result in the exact shape the original endpoint would have returned it inline:

```json
{
  "status": "success",
  "message": "Request completed successfully.",
  "data": {
    "uan_number": "123456789012",
    "employment_history": []
  }
}
```

If `reference_id` is unknown, mistyped, or has expired, you get a 404 instead:

```json
{
  "status": "error",
  "message": "No result found for this reference_id.",
  "error_code": "IDTO_207"
}
```

### Polling guidance

These numbers are taken directly from the current implementation, not estimated:

- **Interval:** poll every 5 seconds. That's the exact value the API sends back in both `retry_after_seconds` and the `Retry-After` header, don't poll faster than that.
- **When to stop, success path:** stop as soon as you get back `status: "success"` or a definitive `status: "error"` with a code other than `IDTO_203` from `GET /verify/result/{reference_id}`.
- **When to give up:** a `reference_id` is only kept for **24 hours** after the job started. Once it expires, the same call returns `404` / `IDTO_207` even if you never got a completed result. Treat that as a hard ceiling, most real integrations should apply a much tighter business timeout (minutes, not hours) and treat a stalled job as failed well before the 24-hour mark.

<Warning>
  A `202` / `IDTO_203` response is never billed. If you stop polling before the job resolves, you were not charged for it. If you want to know the outcome, poll `GET /verify/result/{reference_id}` again later, within the 24-hour window, rather than resubmitting the original request (which starts a new job and could be billed again once it completes).
</Warning>

## Multi-step sessions: bank statement uploads

The bank-statement flow (`/verify/bank_statement_pdf/*`) is async for a different reason: it's an inherently multi-step process (create a session, upload one or more statement files into it, mark it complete, wait for processing, then fetch the report), not one call that's merely slow.

<Steps>

### Start a session

```bash
curl --request POST \
  --url https://prod.idto.ai/verify/bank_statement_pdf/start_upload \
  --header "X-Client-ID: $IDTO_CLIENT_ID" \
  --header "X-API-Key: $IDTO_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{"start_month": "2026-01", "end_month": "2026-06"}'
```

```json
{
  "status": "success",
  "message": "Session created.",
  "data": {
    "session_id": "b6e1f2a0-1234-4abc-9def-0123456789ab",
    "status": "created",
    "expires_at": "2026-09-15T10:15:30Z"
  }
}
```

`expires_at` is set per session by the upload backend, check it on every response rather than assuming a fixed window, it can vary.

### Upload the statement

```bash
curl --request POST \
  --url https://prod.idto.ai/verify/bank_statement_pdf/upload \
  --header "X-Client-ID: $IDTO_CLIENT_ID" \
  --header "X-API-Key: $IDTO_API_KEY" \
  --form "session_id=b6e1f2a0-1234-4abc-9def-0123456789ab" \
  --form "file=@statement.pdf" \
  --form "file_password=1234"
```

You can upload by file, or by `file_url` instead of a multipart file, and you can call this more than once per session if the customer has statements from more than one account.

### Mark the session complete

```bash
curl --request POST \
  --url https://prod.idto.ai/verify/bank_statement_pdf/complete \
  --header "X-Client-ID: $IDTO_CLIENT_ID" \
  --header "X-API-Key: $IDTO_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{"session_id": "b6e1f2a0-1234-4abc-9def-0123456789ab"}'
```

This is what actually kicks off processing. Nothing is analyzed before this call.

### Poll status

```bash
curl --request POST \
  --url https://prod.idto.ai/verify/bank_statement_pdf/status \
  --header "X-Client-ID: $IDTO_CLIENT_ID" \
  --header "X-API-Key: $IDTO_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{"session_id": "b6e1f2a0-1234-4abc-9def-0123456789ab"}'
```

```json
{
  "status": "success",
  "message": "Status fetched.",
  "data": {
    "session_id": "b6e1f2a0-1234-4abc-9def-0123456789ab",
    "status": "processing",
    "txn_status": [
      { "status": "completed", "code": "200", "message": "Upload accepted" }
    ]
  }
}
```

There's no fixed processing SLA published for this flow, poll every 5 to 10 seconds, back off if it runs long, and apply your own reasonable timeout rather than polling indefinitely.

### Fetch the report

Once status shows processing is done, fetch the parsed result:

```bash
curl --request POST \
  --url https://prod.idto.ai/verify/bank_statement_pdf/report \
  --header "X-Client-ID: $IDTO_CLIENT_ID" \
  --header "X-API-Key: $IDTO_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{"session_id": "b6e1f2a0-1234-4abc-9def-0123456789ab", "report_type": "json"}'
```

Set `"report_type": "json"` (the default) for a structured `{summary, transactions}` payload, or a different `report_type` to get a binary file (for example a PDF) back instead, with the appropriate `Content-Type`.

### Cancel if needed

```bash
curl --request POST \
  --url https://prod.idto.ai/verify/bank_statement_pdf/cancel \
  --header "X-Client-ID: $IDTO_CLIENT_ID" \
  --header "X-API-Key: $IDTO_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{"session_id": "b6e1f2a0-1234-4abc-9def-0123456789ab"}'
```

Cancel an open session you no longer need rather than letting it sit unresolved.

</Steps>
