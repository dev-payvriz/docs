title: "Match two faces"
sidebarTitle: "Face match"
description: "Compare a selfie with the photo on an ID document and get a 0 to 100 match score, a confidence band and a match decision."
openapi: "openapi2.0.json POST /v2/verify/face_match"
---

Send two images as `multipart/form-data`: the live selfie in `image1` and the reference photo, usually the face on an ID card, in `image2`. If the reference is already hosted, pass `image2_url` instead of uploading it. idto compares the two faces and returns a score and a decision.

Every response has the same shape whichever source serves the call. Branch on `error_code` and `data.is_match`:

- `error_code: null`, `data.is_match: true`: the faces match. Billed.
- `error_code: null`, `data.is_match: false`: the comparison ran and the faces do not match. Billed, because the check ran to a definitive answer.
- Any non-2xx response: the check did not complete. Never billed.

| Environment | Base URL | Notes |

| Production | `https://prod.idto.ai` | Keys from the dashboard after go-live. Billed. |

## Input rules

| Field | Rule |
|---|---|
| `image1` | Required file. The selfie or live capture. At most 10 MB. |
| `image2` | File. The reference photo. At most 10 MB. Send this or `image2_url`. |
| `image2_url` | A public `https` URL that returns the reference image. Send this or `image2`. |
| `workflow_session_token` | Optional. Pass only when the call is part of an idto workflow session. |

## How the decision is made

| Field | Meaning |
|---|---|
| `data.match_score` | Similarity from 0 to 100. |
| `data.is_match` | `true` when `match_score` is 70 or more. |
| `data.confidence` | `HIGH` at 85 or more, `MEDIUM` from 60 to below 85, `LOW` below 60. |
| `data.extras` | Supplementary image-quality signals. Keys can differ from call to call; do not build logic on them. |
| `billed` | `true` when this call was charged. |

A score between 60 and 70 is `MEDIUM` but not a match. Route those cases to manual review rather than rejecting them outright.

## Retries and duplicate protection

Send an `Idempotency-Key` header (at most 255 characters) to make retries safe. Replaying the same key with the same body within 48 hours returns the stored first response without a new check or a new charge. The same key with a different body returns `IDTO_010` (422). A replay while the first call is still running returns `IDTO_004` (409). If the first call returned an error, nothing is stored, so a retry runs the check again.

## Errors

| Code | HTTP | Message | Billed |
|---|---|---|---|
| `IDTO_001` | 400 | Invalid input: image1 is required. / Invalid input: either image2 or image2_url is required. | No |
| `IDTO_503` | 413 | The image could not be processed. Please try a clearer, smaller image. | No |
| `IDTO_509` | 500 | Face match could not be completed. Please try again. | No |
| `IDTO_001` | 422 | Invalid input. Please check the request and try again. (a required field is missing or has the wrong type) | No |
| `IDTO_009` | 402 | Insufficient credits or balance. Please recharge and try again. | No |
| `IDTO_004` | 409 | An identical request is already in progress; retry shortly. | No |
| `IDTO_010` | 422 | Idempotency-Key was already used with a different request body. | No |
| `IDTO_006` | 429 | Too many requests. Please wait a moment and retry. | No |
| `IDTO_007` | 500 | Verification could not be completed due to a service configuration issue. Please contact support at tech@idto.ai. | No |
| `IDTO_008` | 503 | The verification service is momentarily busy. Please retry shortly. | No |

On `IDTO_503`, resize or re-capture the image. `IDTO_509` means no score could be produced; ask the user for a clearer, front-facing photo and retry. Retry `IDTO_004`, `IDTO_006` and `IDTO_008` with backoff. Full taxonomy: [v2 error codes](/reference/v2-error-codes).
