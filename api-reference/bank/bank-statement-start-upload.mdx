Use this endpoint to start a bank statement analysis, for example to assess income during a loan application. It returns the session you use for every later step. This is a v1 endpoint: the response is a flat object, not the v2 envelope.

## The flow

1. [Start upload](/api-reference/bank/bank-statement-start-upload): open a session, keep `data.session_id`.
2. [Upload](/api-reference/bank/bank-statement-upload): send each statement PDF.
3. [Complete](/api-reference/bank/bank-statement-complete): tell idto every PDF is in.
4. [Status](/api-reference/bank/bank-statement-status): check processing, or wait for the notification on your `txn_completed_cburl`.
5. [Report](/api-reference/bank/bank-statement-report): download the analysis.

[Cancel](/api-reference/bank/bank-statement-cancel) closes a session you no longer need. Every step takes the `session_id` from step 1; idto keeps the session for your account only.

| Environment | Base URL | Notes |

## Billing

Each step is a separate call, charged only when its response `status` is `success`. A charged response carries `chargeble` and `user_consent`, both the string `"true"`, spelled exactly as shown. There is no `billed` field on v1.

A source decline comes back as HTTP 200 with `status: "failed"`, a `message` and an `error_code`, and is not charged. That `error_code` is the source's own reason code (or `IDTO_008` when it gave none), not a stable idto list: branch on `status`.

<Warning>
This endpoint has no `Idempotency-Key` support. A retried call runs again and can be charged twice. Retry only after you have confirmed the first call failed.
</Warning>

## How to read the result

- `status: "success"`: `data.session_id` identifies the session; `data.status` is `started`; `data.expires_at` is when the upload window closes, as the source reports it.
- `txn_completed_cburl` is required. When processing finishes, that URL is notified. Treat the notification only as a signal to call [Status](/api-reference/bank/bank-statement-status); its body is not part of the idto contract.
- `tranx_id` identifies the call for support.

## Errors

Raised errors use the v1 shapes: `{"detail": {...}}` for verification failures, `{"detail": "..."}` for authentication and `{"detail": [...]}` for request validation. Wrapped `detail` objects with `"status": "error"` also carry `tranx_id` and `timestamp`; the session errors below do not.

| HTTP | Body | Billed |
|---|---|---|
| 400 | `{"detail": {"status": "error", "message": "Insufficient credits for this operation.", "error_code": null, ...}}` | No |
| 400 | `{"detail": {"status": "error", "error_code": null, ...}}` when this product is not enabled for your account. Ask your account manager to enable it. | No |
| 401 | `{"detail": "Could not validate credentials"}` when no credentials are sent; `{"detail": "Authentication required. Provide either a valid JWT token, API key + client ID, or SDK token."}` when the key pair is not recognised | No |
| 403 | `{"detail": "Client is inactive"}` or `{"detail": "Customer is inactive"}` | No |
| 404 | `{"detail": "Customer not found for this client"}` | No |
| 422 | `{"detail": [{"type": "missing", "loc": ["body", ...], ...}]}` when a field is missing or has the wrong type | No |
| 400 | `{"detail": {"status": "error", "message": "Transaction completed callback URL is required", ...}}` | No |
| 502 | `{"detail": {"status": "failed", "message": "Upload session could not be initialized"}}` when the source accepted the request but returned no upload session. This is raised after the step was charged; write to tech@idto.ai with the request time. | Yes |
| 502 | `{"detail": {"status": "error", "message": "Invalid response from ... API", ...}}` or `"... returned an empty response"` when the verification source reply is unreadable | No |
| 500 | Our side failed. The body is not part of the contract; retry once after a few seconds (this endpoint has no Idempotency-Key). If it persists, write to tech@idto.ai with the request time. | No |
