Send a UPI ID. idto returns whether it exists and the name registered against it. This is a v1 endpoint: the response is a flat object, not the v2 envelope, and there is no `billed` field.

<Tip>
For new integrations use [UPI ID verification](/api-reference/bank/vpa-verification). It gives you idempotent retries, a `billed` flag and one error format. See [Migrate from v1](/migrate-from-v1).
</Tip>

## Environments

| Environment | Base URL | Notes |
|---|---|---|
| Staging | `https://dev.idto.ai` | Keys on request from your idto account manager. Calls reach live sources, so use identities you are authorised to verify. Staging credits are deducted from your staging account. |
| Production | `https://prod.idto.ai` | Keys from the dashboard after go-live. Billed. |

## Billing

Charged only when the response `status` is `success`. A UPI ID that does not exist can also come back as `status: "success"` with `result.is_valid: false`, and that call is charged. A charged response carries `chargeble` and `user_consent`, both the string `"true"`, spelled exactly as shown. An error response is never charged.

<Warning>
This endpoint has no `Idempotency-Key` support. A retried call runs again and can be charged twice. Retry only after you have confirmed the first call failed.
</Warning>

## Request

| Field | Rule |
|---|---|
| `vpa` | Required. The UPI ID, for example `rahul.sharma@upi`. |
| `name` | Optional. The name you expect on the UPI ID. |
| `user_id` | Optional. Your own reference for the end user. |

## How to read the result

- `status: "success"` with `result.is_valid: true`: the UPI ID exists and `result.vpa_holder_name` is the registered name.
- `result.is_valid: false` with `result.vpa_holder_name: null`: the UPI ID does not exist. Depending on the source enabled for your account this is either a charged `success` or a non-2xx error that is not charged.
- Some accounts also receive `message`, `result.name_match` and `result.name_match_score` when `name` is sent. Treat them as optional.

<Note>
More than one source can serve this endpoint. `status`, `result.vpa_holder_name`, `result.vpa` and `result.is_valid` are present on every successful response whichever source answered, plus `tranx_id` and `timestamp`.
</Note>

## Errors

| Code | HTTP | Body | Billed |
|---|---|---|---|
| none | 400 | `{"detail": {"status": "error", "message": "Insufficient credits for this operation.", "error_code": null, ...}}`: recharge and retry | No |
| none | 400 | Same shape, `message` starting `No vendor configured for customer`: this product is not enabled on your account; write to tech@idto.ai | No |
| none | 401 | `{"detail": "Could not validate credentials"}` (no keys sent) or `{"detail": "Authentication required. Provide either a valid JWT token, API key + client ID, or SDK token."}` (keys not recognised) | No |
| none | 403 | `{"detail": "Client is inactive"}` or `{"detail": "Customer is inactive"}` | No |
| none | 404 | `{"detail": "Customer not found for this client"}` | No |
| none | 422 | `{"detail": [{"type": "missing", "loc": ["body", "..."], ...}]}` when a required field is missing | No |
| varies | 4xx, 502, 503 | `{"detail": {"status": "error", "message": "...", "error_code": ...}}`: the verification source could not complete the call; its status is passed through and `message` varies. Retry later | No |
| none | 500 | Our side failed. Retry once after a few seconds (this endpoint has no Idempotency-Key); if it persists, write to tech@idto.ai with the request time. | No |

Every wrapped `detail` object also carries `tranx_id` and `timestamp`.

## Test scenarios

| Input | Expected result | Billed |
|---|---|---|
| A real, active UPI ID | 200, `status: "success"`, `result.is_valid: true` | Yes |
| A UPI ID that does not exist | 200 with `result.is_valid: false`, or a non-2xx error | Yes for 200, No for an error |
| Body without `vpa` | 422 | No |
