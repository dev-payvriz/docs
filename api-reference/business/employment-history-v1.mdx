Use this endpoint to confirm a person's current and past employers from their UAN. This is a v1 endpoint: the response is a flat object, not the v2 envelope.

## Environments

| Environment | Base URL | Notes |
|---|---|---|
| Staging | `https://dev.idto.ai` | Keys on request from your idto account manager. Calls reach live sources, so use identities you are authorised to verify. Staging credits are deducted from your staging account. |
| Production | `https://prod.idto.ai` | Keys from the dashboard after go-live. Billed. |

<Warning>
This endpoint has no `Idempotency-Key` support. A retried call runs again and can be charged twice. Retry only after you have confirmed the first call failed.
</Warning>

<Tip>
For new integrations use [Employment history](/api-reference/business/employment-history): it supports `Idempotency-Key` retries, returns a `billed` flag and uses one error format. See [Migrate from v1](/migrate-from-v1).
</Tip>

## How to read the result

- `data.employment_data`: one entry per employment, newest information as the source returns it.
- `error_code: "IDTO_201"` with a `detail` object: no history was found. This is still `status: "success"` and is charged. On some account configurations a no-record result is an error instead and is not charged.
- Charged only when the response `status` is `success`. Billing signal: `chargeble` and `user_consent` are present as `"true"` only on a charged call, spelled exactly as shown. There is no `billed` field on v1.
- `tranx_id` identifies the call for support.

<Note>
Depending on how your account is configured, a different source can serve this endpoint. Fields not listed here are passed through as the source returns them and are not a fixed contract. Confirm the fields you rely on in staging before go-live.
</Note>

## Asynchronous handoff

On staging (`dev.idto.ai`) this endpoint can answer HTTP 202 instead of waiting for the source. Production (`prod.idto.ai`) does not do this today and always answers directly. Handle both 200 and 202 so your integration keeps working when production switches it on.

- The 202 body is `{"status": "pending", "error_code": "IDTO_203", "reference_id": "...", "retry_after_seconds": 5, "data": null}` with a `Retry-After: 5` header. It comes back when the result is not ready within about 20 seconds, or when a call with the same UAN from your account is already running.
- Poll [Get async result](/api-reference/business/verify-result) with the `reference_id`. Once the job finishes it returns the status and body this endpoint would have returned.
- The call is charged at most once, when the job finishes with a charged result. The 202 and the polls are not charged. Results are kept for 24 hours.

| none | 400 | `{"detail": {"status": "error", "error_code": null, ...}}` when this product is not enabled for your account. Ask your account manager to enable it. | No |

| none | 404 | `{"detail": "Customer not found for this client"}` | No |
| none | 422 | `{"detail": [{"type": "missing", "loc": ["body", ...], ...}]}` when a field is missing or has the wrong type | No |
| none | 400 | `{"detail": {"status": "error", ...}}`: `uan_number` empty or rejected by the source | No |
| none | 409 | `{"detail": {"status": "error", ...}}`: the source matched too many records | No |
| `IDTO_008` | 503 | `{"detail": {"status": "failed", "message": "The verification service is momentarily busy. Please retry shortly.", "error_code": "IDTO_008", "data": null}}` (not wrapped) when our UAN capacity is busy, or the wrapped body when the source is busy, returned a partial result or timed out | No |

Every wrapped `detail` object also carries `tranx_id` and `timestamp`.
