Use this endpoint to read a person's EPFO details from their UAN when you cannot ask them for an OTP, for example to confirm current and past employers. This is a v1 endpoint: the response is a flat object, not the v2 envelope.

## Environments

| Environment | Base URL | Notes |
|---|---|---|
| Staging | `https://dev.idto.ai` | Keys on request from your idto account manager. Calls reach live sources, so use identities you are authorised to verify. Staging credits are deducted from your staging account. |
| Production | `https://prod.idto.ai` | Keys from the dashboard after go-live. Billed. |

<Warning>
This endpoint has no `Idempotency-Key` support. A retried call runs again and can be charged twice. Retry only after you have confirmed the first call failed.
</Warning>

## Request

| Field | Rule |
|---|---|
| `uan_number` | Required. The 12 digit UAN. |
| `user_id` | Optional. Your own reference for the end user. |

`POST /verify/uan_passbook_without_otp` is a legacy path for the same call. It behaves identically; use the path above for new integrations.

## How to read the result

- `data.employment_data`: one entry per employment, with `establishment_name`, `member_id`, `date_of_joining` and `date_of_exit` when the person has left.
- `data.uan` and `data.uan_list`: the UAN the result belongs to.
- `data.summary`, `data.uan_details`, `data.epfo_details`, `data.pf_filing_details` and `data.establishment_info` are returned as the source provides them and are not a fixed contract.
- `status: "success"` with `error_code: "IDTO_201"` and a top-level `message`: no record was found for the UAN.
- Charged only when the response `status` is `success`. Billing signal: `chargeble` and `user_consent` are present as `"true"` only on a charged call, spelled exactly as shown. There is no `billed` field on v1.
- `tranx_id` identifies the call for support.

<Note>
Depending on how your account is configured, a different source can serve this endpoint, and its payload differs from the one shown here. Confirm the fields you rely on in staging before go-live.
</Note>

## Asynchronous handoff

On staging (`dev.idto.ai`) this endpoint can answer HTTP 202 instead of waiting for the source. Production (`prod.idto.ai`) does not do this today and always answers directly. Handle both 200 and 202 so your integration keeps working when production switches it on.

- The 202 body is `{"status": "pending", "error_code": "IDTO_203", "reference_id": "...", "retry_after_seconds": 5, "data": null}` with a `Retry-After: 5` header. It comes back when the result is not ready within about 20 seconds, or when a call for the same UAN from your account is already running.
- Poll [Get async result](/api-reference/business/verify-result) with the `reference_id`. Once the job finishes it returns the status and body this endpoint would have returned.
- The call is charged at most once, when the job finishes with a charged result. The 202 and the polls are not charged. Results are kept for 24 hours.
