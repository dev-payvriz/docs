Every v2 response from IDTO includes an `error_code` field at the top level of the response envelope. When the call succeeds, `error_code` is `null`. When something goes wrong — or when a query returns no matching record — `error_code` contains an `IDTO_XXX` identifier that tells you exactly what happened and what to do next. Always branch your application logic on `error_code`, not on the HTTP status code or `message` text, because message text can change between API releases.

## v2 vs v1 Error Envelopes

The two API versions surface errors differently. Prefer v2 for new integrations.

<Tabs>
  <Tab title="v2 (Recommended)">
    v2 returns a flat envelope. The `error_code` field is always present and is `null` on success:

    ```json
    {
      "status": "error",
      "message": "User consent not provided",
      "error_code": "IDTO_005",
      "data": null,
      "billed": false,
      "tranx_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
      "timestamp": "2026-07-11T10:20:30.123456"
    }
    ```
  </Tab>
  <Tab title="v1 (Legacy)">
    v1 wraps error detail inside a `detail` object, making programmatic handling less predictable:

    ```json
    {
      "detail": {
        "status": "error",
        "message": "User consent not provided",
        "error_code": "IDTO_005"
      }
    }
    ```
  </Tab>
</Tabs>

## IDTO Error Code Reference

<Warning>
  **`IDTO_202` is not a failure.** It means the request was processed successfully, a credit was consumed, but no matching government record was found for the input you provided. Do not treat it as a hard error — handle it as a valid "no record" outcome.
</Warning>

| Error Code | HTTP Status | Meaning | Recommended Action |
|-----------|------------|---------|-------------------|
| `IDTO_001` | 400 / 422 | Invalid or missing field in the request | Check the `message` field for the specific field name. Fix the request body and retry. |
| `IDTO_004` | 409 | Duplicate idempotency key | You sent the same idempotency key for a different request. Use a new unique key for each distinct request. |
| `IDTO_005` | 400 | User consent not provided | Add `"user_consent": true` to the request body. |
| `IDTO_006` | 429 | Rate limit exceeded | Back off and retry after the interval indicated in the `Retry-After` response header. |
| `IDTO_007` | 500 | Service configuration error | This is an IDTO-side issue. Retry once after a short delay; if it persists, contact [tech@idto.ai](mailto:tech@idto.ai) with the `tranx_id`. |
| `IDTO_008` | 503 | Service temporarily unavailable | The upstream government data source is unreachable. Retry with exponential back-off. |
| `IDTO_009` | 402 | Insufficient credits | Top up your IDTO account balance before retrying. |
| `IDTO_202` | 200 | No matching record found — **billed** | The request was valid and processed. No government record matched the input. Handle as a "not found" result, not an error. |
| `IDTO_203` | 202 | Verification in progress — use async polling | The result is not yet ready. Poll `GET /v2/verify/result/{reference_id}` until the status changes. |
| `IDTO_204` | 422 | No readable QR found in the uploaded image | Ensure the Aadhaar QR code is clearly visible, well-lit, and unobstructed, then re-upload. |
| `IDTO_205` | 422 | Wrong OTP or expired OTP session | The OTP entered is incorrect or the session has timed out. Restart the OTP flow from the initiation step. |
| `IDTO_206` | 429 | Maximum OTP attempts exceeded | The user has exhausted all OTP attempts for this session. Start a new session. |
| `IDTO_207` | 404 | Async result not found | The `reference_id` does not match any pending or completed async job. Verify the ID and retry, or re-submit the original request. |

<Note>
  **Async flows and `IDTO_203`:** When you receive `IDTO_203`, the `data` object in the response contains a `reference_id`. Poll `GET /v2/verify/result/{reference_id}` at a reasonable interval (e.g., every 2–5 seconds) until `error_code` is no longer `IDTO_203`.
</Note>

## HTTP Status Code Reference

| HTTP Status | Typical Meaning | Common IDTO Error Codes |
|------------|----------------|------------------------|
| `200 OK` | Request processed successfully | `null` (success), `IDTO_202` (no record, billed) |
| `202 Accepted` | Request accepted, result pending | `IDTO_203` |
| `400 Bad Request` | Malformed request or business rule violation | `IDTO_001`, `IDTO_005` |
| `401 Unauthorized` | Missing or invalid authentication credentials | — (auth error, no IDTO code) |
| `402 Payment Required` | Insufficient account credits | `IDTO_009` |
| `404 Not Found` | Resource or async result does not exist | `IDTO_207` |
| `409 Conflict` | Duplicate idempotency key | `IDTO_004` |
| `413 Payload Too Large` | Uploaded file or request body exceeds size limit | — |
| `422 Unprocessable Entity` | Validation error or unprocessable input | `IDTO_001`, `IDTO_204`, `IDTO_205` |
| `429 Too Many Requests` | Rate limit or OTP attempt limit exceeded | `IDTO_006`, `IDTO_206` |
| `500 Internal Server Error` | Unexpected server-side error | `IDTO_007` |
| `503 Service Unavailable` | Upstream government service is unreachable | `IDTO_008` |

## Handling Error Codes in Code

The example below shows a complete error-handling pattern in Python. Notice that the branching is entirely on `error_code` — not on `response.status_code` or `body["message"]`.

```python Python
import os
import time
import requests

def verify_pan(pan_number: str) -> dict:
    url = "https://prod.idto.ai/v2/verify/pan_validation"
    headers = {
        "X-Client-ID": os.environ["IDTO_CLIENT_ID"],
        "X-API-KEY":   os.environ["IDTO_API_KEY"],
    }
    payload = {"pan_number": pan_number, "user_consent": True}

    response = requests.post(url, json=payload, headers=headers)
    body = response.json()
    error_code = body.get("error_code")

    # --- Success ---
    if error_code is None:
        return body["data"]

    # --- No record found (still billed) ---
    if error_code == "IDTO_202":
        print(f"No government record found for PAN: {pan_number}")
        return {}

    # --- Async result not yet ready ---
    if error_code == "IDTO_203":
        reference_id = body["data"]["reference_id"]
        return poll_async_result(reference_id, headers)

    # --- User consent missing ---
    if error_code == "IDTO_005":
        raise ValueError("Set user_consent=True before calling this endpoint.")

    # --- Insufficient credits ---
    if error_code == "IDTO_009":
        raise RuntimeError("Insufficient IDTO credits. Please top up your account.")

    # --- Rate limit ---
    if error_code == "IDTO_006":
        retry_after = int(response.headers.get("Retry-After", 5))
        print(f"Rate limited. Retrying in {retry_after}s …")
        time.sleep(retry_after)
        return verify_pan(pan_number)  # single retry

    # --- Transient server errors ---
    if error_code in ("IDTO_007", "IDTO_008"):
        print(f"Transient error ({error_code}). Retrying in 5s …")
        time.sleep(5)
        return verify_pan(pan_number)  # single retry

    # --- Unhandled error code ---
    raise RuntimeError(
        f"Verification failed [{error_code}]: {body.get('message')} "
        f"(tranx_id={body.get('tranx_id')})"
    )


def poll_async_result(reference_id: str, headers: dict, max_attempts: int = 10) -> dict:
    url = f"https://prod.idto.ai/v2/verify/result/{reference_id}"
    for attempt in range(max_attempts):
        time.sleep(3)
        response = requests.get(url, headers=headers)
        body = response.json()
        if body.get("error_code") != "IDTO_203":
            return body.get("data", {})
    raise TimeoutError(f"Async result not ready after {max_attempts} attempts.")
```

<Note>
  Always log the `tranx_id` returned in every response — even failures. It is the primary identifier the IDTO support team uses to investigate issues. Never rely on `message` text for branching: it is human-readable and subject to change without notice.
</Note>
