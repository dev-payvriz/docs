## General

<AccordionGroup>
  <Accordion title="Which PAN endpoint should I start with?">
    Start with [PAN Validation](/api-reference/pan/pan-validation) if you only need to know the PAN is real and active and want the name on record. Use [PAN Detailed](/api-reference/pan/pan-detailed) when you also need address, masked Aadhaar, gender, DOB or linked bank accounts. Use [PAN OCR](/api-reference/pan/pan-ocr) to prefill the number from a photo of the card.
  </Accordion>
  <Accordion title="Am I charged when the PAN has no record?">
    Yes on v2. A no-record result is a definitive answer: HTTP 200, `status: "success"`, `error_code: "IDTO_202"`, `billed: true`. Errors (bad format, missing consent, rate limits, service errors) are never charged. On the v1 endpoints a `status: "failed"` result is not charged.
  </Accordion>
  <Accordion title="Why do I have to send user_consent?">
    The v2 PAN lookups need the end user's consent to fetch their record. Send `user_consent: true` only after you have recorded that consent. `user_consent: false` returns `IDTO_005` (400) and is not charged.
  </Accordion>
  <Accordion title="Does PAN OCR confirm the PAN is real?">
    No. OCR only reads the card. Call PAN Validation on the number you read, after the user confirms it, to check it against the record.
  </Accordion>
  <Accordion title="What does the holder category mean?">
    It is read from the fourth character of the PAN: `P` individual, `C` company, `H` HUF, `F` firm, `A` AOP, `T` trust, `B` BOI, `L` local authority, `J` artificial juridical person, `G` government. Any other character gives `unknown`.
  </Accordion>
  <Accordion title="Should I move from pan_nsdl or pan_all_in_one to v2?">
    For new work, yes. v2 gives you `Idempotency-Key` support, a `billed` flag on every response and one error format. `pan_all_in_one` maps to `pan_detailed`. `pan_nsdl` matches a name and DOB you supply; there is no v2 endpoint with the same match flags today, so keep using it for that check. See [Migrate from v1](/migrate-from-v1).
  </Accordion>
</AccordionGroup>

## Technical

<AccordionGroup>
  <Accordion title="How do I tell a found PAN from a missing one?">
    Read `error_code`, not `status`. `null` with `data` means found. `IDTO_202` with `data: null` means no record. Both come back with `status: "success"`.
  </Accordion>
  <Accordion title="What format must pan_number follow?">
    Ten characters: five letters, four digits, one letter, in upper case, for example `ABCDE1234F`. An empty value or a wrong shape returns `IDTO_001` (400) before any lookup runs, so it is not charged. A body without the field at all returns `IDTO_001` with HTTP 422.
  </Accordion>
  <Accordion title="How do I retry safely after a timeout?">
    Send the same `Idempotency-Key` header with the same body. You get the stored first response back and are not charged again. If the first call is still running you get `IDTO_004` (409); wait and retry. Reusing a key with a different body returns `IDTO_010` (422). v1 PAN endpoints do not support this header.
  </Accordion>
  <Accordion title="Which PAN detailed fields can be empty?">
    Most fields can be missing for a given PAN, depending on what the record holds. `gender`, `email`, `phone_number`, `masked_aadhaar` and `dob` can be `null`; `bank_details` can be an empty list. Write your code to treat each field as optional.
  </Accordion>
  <Accordion title="Why are email, phone and account numbers masked?">
    PAN Detailed masks personal data before it leaves idto: email keeps the first two characters of the local part, phone keeps the last two digits, Aadhaar and bank account numbers keep the last four digits.
  </Accordion>
  <Accordion title="What files does PAN OCR accept?">
    JPEG, PNG or PDF in a multipart field named `file`. Keep it under 5 MB; larger files can return `IDTO_503` (413). Other types or an empty file return `IDTO_001` (400).
  </Accordion>
  <Accordion title="Why was a call inside a workflow returned with billed false?">
    When you pass `workflow_session_token` for a workflow that already charges for the PAN step, the individual call is not charged again and `billed` is `false`.
  </Accordion>
</AccordionGroup>
