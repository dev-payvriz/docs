## General

### What is the difference between penny drop and pennyless verification?

`/v2/verify/bank_verification` credits a small deposit to the account and returns a fixed response shape, with idempotency support. `/verify/bank_verification/pennyless` is a v1 endpoint that checks the account without a deposit; its fields come back as the bank network returns them and it has no idempotency support. Use the v2 endpoint for new integrations.

### Does idto match the name I send against the name on the account?

No. `name` is optional and is not scored. Compare `data.account_holder_name` in the response with the name you hold, using the matching rule your risk policy needs. Decide in advance how strict the comparison should be and when a mismatch goes to manual review.

### What does a successful response contain?

`account_status` (always `VALID` on a success), `account_holder_name` as the bank holds it, `account_number` masked to its last 4 digits, `account_ifsc` in upper case, `utr` (the bank network's reference for the deposit, when the network returns one) and `failure_reason`. Treat `utr` and `failure_reason` as optional; either can be `null`.

### Can I test without being charged?

There is no sandbox. Staging (`https://dev.idto.ai`) reaches live bank networks and deducts credits from your staging account, so use an account you are authorised to verify. The [Test scenarios](/api-reference/bank/bank-verification#test-scenarios) table lists inputs that return each error without running a penny drop.

## Input and validation

### Which input formats are accepted?

`account_number`: 6 to 40 letters or digits, no spaces or symbols. `ifsc` (or `ifsc_code`): 4 letters, a zero, then 6 letters or digits, any case. `reference_id`: 1 to 40 letters, digits or hyphens. Anything else returns `IDTO_001` (400) before any charge. A body without `account_number` or `ifsc` at all returns `IDTO_001` with HTTP 422.

### What do IDTO_401 and IDTO_402 mean?

The bank network rejected the account number (`IDTO_401`) or the IFSC (`IDTO_402`) as invalid. Neither is billed. Ask the user to check the details instead of retrying the same input.

### Should I strip spaces from the account number myself?

Yes. Leading and trailing spaces are trimmed, but spaces or hyphens inside the number fail the format check with `IDTO_001` (400). Remove them before you call.

## Billing

### Am I charged when the account is invalid?

Yes, on `/v2/verify/bank_verification`. An invalid, closed or non-existent account returns HTTP 200 with `error_code: "IDTO_202"` and `billed: true`, because the check ran to a definitive answer. Any non-2xx response is never billed.

### What happens when my balance is too low?

The call is rejected before any penny drop with HTTP 400, `error_code: null` and the message "Insufficient credits for this operation." It is not billed. Recharge, then retry.

### Why does a call inside a workflow come back with billed false?

When you pass `workflow_session_token` for a workflow that already charges for the bank step, the individual call is not charged again and `billed` is `false`.

### How do I tell a charged v1 pennyless call from an uncharged one?

A charged response has `status: "success"` and carries `"chargeble": "true"` and `"user_consent": "true"`. Any other response was not charged.

## Retries and duplicates

### What happens if I send the same request twice?

Without an `Idempotency-Key`: while the first request is running, an identical second request (same body) gets `IDTO_004` (409) and is not charged. After the first finishes, an identical request runs a new penny drop and is billed again. With an `Idempotency-Key`: a replay with the same body within 48 hours returns the stored first response without a new charge. Reusing a key with a different body returns `IDTO_010` (422).

### My request timed out. Was I charged?

If the check finished on idto's side, yes. Send every request with an `Idempotency-Key`, then retry with the same key and body: you get the stored result and no second charge. If the first call ended in an error, nothing is stored and the retry runs the check again. See the [idempotent retry recipe](/recipes/pan-ocr-idempotent-retry).

### Which errors should I retry?

Retry `IDTO_004` (409), `IDTO_006` (429), `IDTO_008`, `IDTO_103` and `IDTO_403` (503) with backoff, using the same `Idempotency-Key`. Do not retry `IDTO_001`, `IDTO_401`, `IDTO_402` or `IDTO_010` without changing the request. `IDTO_007` (500) means the service is not set up correctly for your account: contact support rather than retrying.

## End users

### What should I show the user for each outcome?

On success, show the registered name and ask the user to confirm it is their account. On `IDTO_202`, `IDTO_401` or `IDTO_402`, ask them to check the account number and IFSC, or to give a different account. On a 409, 429 or 503, keep the user waiting and retry in the background; the account itself is not the problem. Never show the full account number back; use the masked value from the response.
