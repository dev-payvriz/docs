Prefer a collection? Import the [Postman collection](https://idto-sdk-bucket.s3.ap-south-1.amazonaws.com/docs/v1/postman/idto-api-2026-10.postman_collection.json) and set your base URL and key pair in its variables.

<Steps>

### Get credentials

Every call to idto needs two headers: `X-Client-ID` and `X-API-Key`. Ask your IDTO account manager for staging keys and build against `https://dev.idto.ai`. Staging calls reach live verification sources and deduct staging credits, so use only identities you are authorised to verify. Production keys come from the dashboard after go-live; then switch the base URL to `https://prod.idto.ai`.

| Environment | Base URL | Notes |
| --- | --- | --- |
| Production | `https://prod.idto.ai` | Keys from the dashboard after go-live. Billed. |
| Staging | `https://dev.idto.ai` | Keys on request from your IDTO account manager. Calls reach live sources, so use identities you are authorised to verify. Staging credits are deducted from your staging account. |

See [Environments](/environments) and [Authentication](/authentication) for the detail.

```bash
export IDTO_CLIENT_ID="your_client_id"
export IDTO_API_KEY="your_api_key"
```

### Make a call

`POST /v2/verify/pan_validation` is the smallest useful call: it checks whether a PAN exists and is active, and returns the name and holder category on file. `pan_validation` requires `user_consent: true` in the body: the call is rejected with `IDTO_005` (400) without it. Consent is required per product; each endpoint page says whether it applies.

<CodeGroup>

```bash cURL
curl --request POST \
  --url https://dev.idto.ai/v2/verify/pan_validation \
  --header "X-Client-ID: $IDTO_CLIENT_ID" \
  --header "X-API-Key: $IDTO_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "pan_number": "ABCDE1234F",
    "user_consent": true
  }'
```

```python Python
import os
import requests

response = requests.post(
    "https://dev.idto.ai/v2/verify/pan_validation",
    headers={
        "X-Client-ID": os.environ["IDTO_CLIENT_ID"],
        "X-API-Key": os.environ["IDTO_API_KEY"],
    },
    json={"pan_number": "ABCDE1234F", "user_consent": True},
)
print(response.json())
```

</CodeGroup>

### Read the response

A match returns HTTP `200` with the PAN holder's name and status:

```json
{
  "status": "success",
  "message": "PAN verified successfully.",
  "error_code": null,
  "data": {
    "pan_name": "RAHUL SHARMA",
    "pan_number": "ABCDE1234F",
    "pan_status": "Active",
    "category": "individual"
  },
  "billed": true,
  "tranx_id": "8f14e45f-ceea-467e-bd93-4a2c11e0a1b2",
  "timestamp": "2026-09-14T10:15:30Z"
}
```

Four fields drive your integration logic:

| Field | What it tells you |
| --- | --- |
| `status` | `"success"` for any 2xx response, `"error"` for anything raised. There's no `"failed"` value anywhere in v2. |
| `error_code` | `null` on a full match. An `IDTO_*` code on a no-record result or a raised error, for example a request without `user_consent` returns `IDTO_005`. |
| `data` | The verification result. `null` whenever `error_code` is set. |
| `billed` | Whether this call consumed a credit. A definitive no-record result is still `billed: true`, since it still cost a verification. |

This is the same four-field shape on every v2 endpoint, not just PAN. Read [Request & Response](/concepts/request-response) for the complete envelope reference, including how multipart (image upload) endpoints differ, and [Error Codes](/error-codes) for how to branch on every outcome.

### Handle the other outcomes

| HTTP | `error_code` | Meaning | Billed |
| --- | --- | --- | --- |
| 200 | `null` | Full result in `data` | Yes |
| 200 | `IDTO_202` | No record for this PAN | Yes |
| 400 | `IDTO_001` | PAN format is wrong | No |
| 400 | `IDTO_005` | `user_consent` missing or not `true` | No |
| 401 | none | Missing or wrong key pair | No |
| 503 | `IDTO_008` | Busy, retry with backoff | No |
